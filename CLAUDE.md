# ThaiKaraoke — Project Conventions

A fully client-side PWA for learning spoken Bangkok Thai to ~84% coverage.
Karaoke (Paiboon-style romanization) first, FSRS spaced repetition, 7 quiz
modes, Tone Gym, offline-capable, installable.

## Hard constraints (do not violate)

- Static site, NO build step. Vanilla JS ES modules + HTML + CSS only.
- No npm dependencies in the app. No frameworks, no bundlers.
- Runs via any static server (`python3 -m http.server 8000`), works fully
  offline after first load (service worker caches everything).
- All state in `localStorage` under key `thaikaraoke.v2`, autosaved after
  every answer. Export/import JSON with `schemaVersion`.
- Audio only via `speechSynthesis` with a `th-TH` voice.

## Data conventions

- Word ids `w0001`..`w1200` == rank order. Phrase ids `p0001`..`p0400`.
  Minimal pair set ids `mp01`..`mp60`.
- Data files are ES modules: `export const words = [...]` /
  `export const phrases = [...]` / `export const minimalPairs = [...]`.
  They are also loaded by Node scripts via dynamic `import()`.
- Karaoke is Paiboon-style: tone diacritics on the vowel
  (mid = unmarked, low = grave à, falling = circumflex â, high = acute á,
  rising = hàček/caron ǎ) and long vowels doubled (aa, ii, uu, ɛɛ, ɔɔ, əə,
  ʉʉ, oo, ee). Multisyllable karaoke separates syllables with `-`;
  phrase karaoke separates words with spaces.
- `tone` is a string for monosyllables, an array (one entry per syllable)
  for multisyllables. Valid values: mid | low | falling | high | rising.
- The validator cross-checks `tone` against karaoke diacritics per
  syllable. Keep them consistent.
- Words 1–150 are the curated survival set; 151+ approximate spoken
  frequency order.
- Phrase `thai` and `karaoke` are word-spaced (spaces between words, which
  is not how Thai is written but enables tokenization); `wordIds` and word
  `exampleIds` are generated by `scripts/link-data.mjs` from those tokens —
  do not hand-edit them, re-run the linker instead.

## Code conventions

- ES modules, no globals except what `app.js` wires up.
- Pure logic (fsrs.js, coverage.js, session queue building) must not touch
  DOM or localStorage, so Node test scripts can import them.
- Screens render into their own `<section>`; `app.js` toggles visibility.
- Tone colors (used everywhere, incl. legend): mid #9aa0a6, low #4d9de0,
  falling #b07ce8, high #ff9f43, rising #2ecc8f. Accent color: #ff9f43
  family (single accent). Dark background default.
- After any data file change: `node scripts/link-data.mjs && node
  scripts/validate-data.mjs` and fix everything flagged.

## Session recovery

PROGRESS.md is the single source of truth for build status. Update it as
steps complete. If resuming an interrupted session: read PROGRESS.md,
run both node scripts, and continue at the first unchecked item.

## Schema v2 (state.js)

The stored document is split in two:

- **syncable** — facts only. Append-only logs (`reviews`, `sessions`,
  `microLessonsShown`, `coverageSnapshots`, `reviewsDaily`) and keyed
  last-write-wins objects (`cards`, `settings`, `frameProgress`, each stamped
  with `updatedAt`/`updatedBy`).
- **`_local`** — device-only: session resume point, mode history, in-flight
  timer, gist id, access token, sync bookkeeping. Never pushed, never merged.

Timestamps are epoch milliseconds. Day keys are `YYYY-MM-DD`: local dates for
anything the user sees (streak, charts, daily caps), UTC for rollup aggregates
so two devices produce identical keys.

**Derive, never store.** No counter is ever written down — not the streak, not
cards-done-today, not tone accuracy, not hours. They are all computed in
`derive.js` from the logs. Two devices cannot disagree about a number neither
of them stores. Adding a stored counter breaks sync; add a derivation instead.

`merge.js` has exactly two rules: keyed objects take the entry with the greater
`updatedAt` (ties broken by `updatedBy`, then canonical JSON, so the merge is
commutative), and logs are unioned by `id` then canonically sorted. It is pure
and covered by `scripts/test-merge.mjs`.

`rollup.js` folds reviews older than 180 days into `reviewsDaily` aggregates
keyed `date|mode|tone`, and merge drops any review whose key already has an
aggregate. Known limitation: a device offline for more than 180 days can carry
reviews that the others have already summarized; they are dropped rather than
double-counted, so its old per-review detail is lost while the totals stay
right.

Sync runs on load, at session end, on manual request, and 2s after the tab is
hidden — never mid-session, because the resume point is device-local. The
access token lives only in `_local`, is sent only to api.github.com, and is
never logged or committed.

## Frames and lessons

`data/frames.js` and `data/pools.js` are generated by
`scripts/build-frames.mjs`; `data/phrases-09.js` by
`scripts/build-phrases-09.mjs`. Both compose Thai and karaoke from lexicon
words so tone marks and token counts are correct by construction. Edit the
generator, then re-run `node scripts/link-data.mjs && node
scripts/validate-data.mjs`.

The frame engine only ever fills a slot with a word whose card exists and is
no longer `new`, so a drill never introduces unseen vocabulary. Frames own no
FSRS cards: a frame answer grades the word that filled the slot and logs
`mode:"frame"`.
